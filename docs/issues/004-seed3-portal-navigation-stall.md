## 复现

在项目根目录、Node 环境下执行：

```powershell
node test/diag.portal.js 3
```

该诊断脚本输出四行 JSON，四组实验开门前的种子、基因、战斗与玩家状态一致，
仅在区域守卫后的传送门开启时改变一个参数。脚本固定 v1.9 原始小怪数值，避免 v1.10 的提前阵亡掩盖旧场景；
v1.11 起直接从 git 提交 `458bd1a` 加载历史源码（需要本地 git 历史），避免武器／英雄修正改变战斗前置路径。
诊断过程不写入存档或修改源码。

也可通过现有仿真入口观察原始超时：

```powershell
node -e "const {simulateRun}=require('./test/lib.js'); const {ORIGINAL}=require('./test/enemy-balance.js'); const r=simulateRun(3,{quiet:true,enemyTuning:ORIGINAL}); console.log(r.outcome,r.errors);"
```

输出 `timeout` 与停滞快照。v1.9 的 sim.test.js 对该情况整体仍退出 0；v1.10 已加强故障断言。

## 预期与实际行为

预期：区域守卫击破、传送门开启后，AI 能走到门前并通过正常交互进入第 4 区。

实际：164.03 游戏秒时，Boss 已死亡（`bossRef.dead=true`、`bossDown[2]=true`），
传送门在 `(200,200)` 开启，玩家在 `(270.51,58.90)`。随后玩家持续绕行，
到 660 秒仍停在第 3 区；开门后累计移动 41245.57px，最近门距仍为 131.58px，无法触发交互。
传送门位置通过玩家碰撞盒空地检查；`bossRef.st` 残留 `dying` 字段不表示死亡流程尚未结束。

## 诊断证据

当前完整流程标尺为 `commit=45,trackK=2,sight=85,delay=15,dashSkip=0.85`。

| 开门后的处理 | 进入第 4 区 | 最近门距 |
| --- | --- | --- |
| 保持原始参数 | 到 660s 仍未进入 | 131.58px |
| 仅关闭移动惯性（commit=0） | 开门后 2.50s | 13.60px |
| 仅缩短移动惯性（commit=10） | 开门后 2.63s | 13.71px |
| 仅关闭感知延迟（delay=0） | 到 660s 仍未进入 | 131.58px |

证据支持移动惯性与 BFS 路点跟随冲突：bot 选定方向后继续保持 45 帧，
包括选方向当帧共 46 帧；基础速度下目标位移约 73.6px，而路点相距 16px，路径每 0.3s 重算。
玩家越过路点后仍沿旧方向移动，重算后又追逐局部路点，形成持续绕行。
本例 29758 个导航帧中，12168 帧的实际输入与当前导航合力方向相反。

防卡死检测只累计低位移，持续移动使 `stuckT` 最大仅 0.52s；战斗进展看门狗又依赖存活敌人，
因此二者都无法捕捉 Boss 击破后的“有运动、无导航进展”。

验收漏报原因：`simulateRun` 将超时写入 `r.errors` 并返回 `ok=false`，
但种子局和英雄局仅打印这些错误。只要其他局满足聚合胜利条件，整体仍可以成功退出。

## 后续修复方向

- 在传送门导航阶段暂停移动承诺，或在到达/越过路点时中断承诺；保留战斗中的人类化惯性。
- 增加区域守卫击破后的限时导航回归，捕捉有位移但无进展的情况。
- 区分仿真结局：胜利、阵亡、超时、异常。允许难度导致阵亡，但超时和异常必须使验收失败。
